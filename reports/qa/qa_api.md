## 4. Open issues
- **Time remaining in the UI (user request).** Since 02:37 the API has `eta_s`, `eta_total_s`, `eta_basis`, `stage_fraction`, `stage_elapsed_s`, `bytes_done` / `bytes_total`, `rows_done` and `ingest_mb_s` (test_qa_api.py RUN_KEYS / `_check_progress_types` and the probe now pin this key set). Measured accuracy is above. Two problems remain: QA-API-06, and ingest bytes_done / stage_fraction topping out near 40-45 % (not reproducible in a unit test because it depends on DuckDB query_progress). On a contended machine the history (from idle runs) underestimates by up to 73 % of total. The UI should show the ETA as approximate and label `eta_basis`. Use `eta_s`, never a value derived from `percent`: `percent` alone would be off by 54-90 % of total (calibration table above).
- The integrations router allows client hosts `testclient` and `localhost` by name (`_client_ok`). Same low risk as `testserver` in `DEFAULT_HOSTS`.
- Live latency target (TESTING.md §7: under 5 s) was missed: 13-17 s. This was measured only under full CPU contention with
  threads 2. A run on an idle machine with default threads is needed before the target can be called a pass or a fail.
  Per-cycle cost is dominated by re-running detect over the window, not by ingest.
- The engine has no graceful stop on Windows except Ctrl+C in its console. `terminate()` skips the final
  `running=false` write, so the API reports disabled only once the heartbeat is stale (9.3-9.6 s).
- After the pinned run's out dir is deleted, the API keeps serving it (0 incidents, `out_dir_source` = `api_run`)
  until restart. There is no fallback to `ATTACKLENS_OUT` or newest.
- `HEAD /api/health` gives 405. FastAPI GET routes do not answer HEAD, so health checks that use HEAD fail.
- `DEFAULT_HOSTS` trusts `testserver` in production (api_guard.py). It is a single-label name, so the risk is low; worth
  removing outside tests.
- `POST /api/runs` without `out_dir` writes `data/out/<set>` and overwrites an earlier output of the same set that is
  not being served. This is documented behaviour, not a bug. The probe always passed an explicit out_dir.
- The upload root has no override (pipeline.yaml `upload.root`). The probe used `data/raw/uploads` and removed it
  afterwards; it did not exist before.
- Full fast suite (`pytest backend -q -m "not stress"`, 27 min 46 s, contended): 1416 passed, 33 failed, 3 skipped,
  21 xfailed. All 33 failures are in `backend/tests/test_integrations.py` (SIEM connectors). The errors were
  `httpc has no attribute 'with_retries'` and `request_json() got an unexpected keyword argument 'ca_file'`. Another
  agent was writing the untracked `backend/attacklens/httpc.py` while the suite ran (mtime 00:52), and it now has both.
  A re-run of only `test_integrations.py` afterwards gave 47 passed, 0 failed. So this was a race with work in
  progress, not a qa_api finding. No failures in `backend/tests/qa/test_qa_api.py`. Log: `data/tmp/qa_api/fast_suite.log`.
- Full fast suite run 3 (`pytest backend -q -m "not stress"`, 57 min 53 s, contended; log `data/tmp/qa_api/fast_suite3.log`): 1668 passed, 12 failed, 3 skipped, 33 xfailed. Of the 12: 1 was `test_qa_api.py::test_concurrent_post_runs_one_202_then_served_switch`, because the suite imported the file before another agent extended RUN_KEYS for the new progress keys (02:06). It passes on the current file: `test_qa_api.py` + `test_qa_api_routes.py` = 113 passed, 7 xfailed. The other 11 (`test_cloud_connectors.py` Azure / Sentinel / GCP x 9, `test_api_integrations.py::test_sink_connection_test_hec` (`permission_denied` != `auth_failed`), `test_integrations.py::test_failure_inside_tie_group...[sentinel]` (1 s mock timeout)) are outside this track. Connector code was being edited while the suite ran. They are not triaged here.
