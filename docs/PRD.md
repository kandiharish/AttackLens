# PRD — Kill Chain and Attack Path Analysis (organiser's brief, condensed)

Source: "PRD: Kill Chain and Attack Path Analysis — Problem, Goals and Requirements", 30 Oct 2026, plus the
Mitigata CyberForge rules page. Do not edit this file except to correct it against the original.

## 1. Problem
A company with a few hundred laptops, servers and users. An attacker guessed a password, got onto a laptop,
moved to a file server and copied data out. Each step left one line in a log, spread across different files,
millions of lines apart. Security tools raise alerts one at a time, so:
- No complete story: "failed login", "new admin account", "big upload" look like three separate alerts.
- Manual linking takes an expert hours.
- Nobody can tell if an alert is noise or step three of a break-in; ATT&CK mapping is done by hand, late.

**Challenge:** take a large log data set, detect suspicious activity, map it to MITRE ATT&CK techniques and
kill-chain stages, rebuild the attack path across hosts, users, accounts and time, show what happened and what
the attacker could reach next. Same data set as the Log Parser problem. Any approach, any stack.

## 2. Goals
Detect · Label (technique + kill-chain stage) · Connect (one attack path story) · Explain (timeline + path an
analyst understands in a minute) · Look ahead (what the attacker can reach next) · Accurate (matches planted
ground truth, few false alarms) · Scales (15 GB+ on a normal machine).
Not required: polished UI, login/user management/cloud deployment, blocking the attack.

## 3. Functional requirements
| ID | Must have | Example |
|---|---|---|
| FR-1 | Read the full data set without loading it all into memory | 15 GB tier on a 16 GB laptop |
| FR-2 | Detect suspicious events | 50 failed logins on one account, then a success |
| FR-3 | Map each detection to an ATT&CK technique and a kill-chain stage | "Brute Force (T1110)" → Credential Access |
| FR-4 | Link related events into one incident by host, user, IP and time | failed logins + new admin account + upload to outside IP = one attack |
| FR-5 | Show the attack path as a timeline and as a graph of hosts and users | Laptop HR-07 → file server FS-02 → DC-01 |
| FR-6 | Show what the attacker could reach next | "This account has admin rights on 3 more servers" |
| FR-7 | Simple API or page, with a short README | `GET /incidents/12/path` |

| ID | Bonus (any) |
|---|---|
| B-1 | Risk score per incident, worst on top |
| B-2 | Auto-written incident report in plain English |
| B-3 | How many raw alerts were merged into each incident |
| B-4 | Add a detection rule by editing a config file (e.g. Sigma), not code |
| B-5 | Live mode: new log lines update the attack path within seconds |

## 4. Data tiers and targets
| Tier | Size (uncompressed) | Tests | Score multiplier |
|---|---|---|---|
| Core | 15 GB | Bigger than laptop memory: stream and chunk | 1.0× |
| Advanced | 30 GB | Parallel processing and compact storage | 1.3× |
| Extreme | 50 GB | Full scale; multi-core machine expected | 1.6× |

- Same formats and the same planted attack sequences in every tier.
- **Accuracy gate:** a bigger tier earns more only if accuracy stays above the minimum bar.
- A 100 MB dev sample is shared at kickoff; full tiers are downloaded when the build starts.

| Measure | How | Good | Great |
|---|---|---|---|
| Detection | Share of planted attack steps found | > 70 % | > 90 % |
| Correct labels | Share of found steps with the right ATT&CK technique | > 60 % | > 85 % |
| Attack path | Planted attacks rebuilt with right steps in right order | half | all |
| False alarms | Share of our incidents that are not real attacks | < 30 % | < 10 % |
| Processing time | Full chosen tier | < 3 h | < 1 h |
| Memory | Peak while processing | < 16 GB | < 8 GB |
| Investigation speed | Open one incident's attack path | < 2 s | < 500 ms |

Suggested (not mandatory): Python/Go/Rust parsing; DuckDB/ClickHouse/Elasticsearch storage; Neo4j/NetworkX
graph; Sigma rules and the MITRE ATT&CK data set. **Must run easily from the README; Docker Compose is a plus.**

## 5. Hackathon rules that affect the build
- Original work built for this hackathon; **disclose all third-party tools, APIs, datasets, open-source components.**
- Team of exactly 2. Solution must be functional and demonstrable live. AI tools are allowed.
- Security testing only on provided/authorized data and systems. No malware or harmful payloads.
- Provided datasets are confidential: use only for the hackathon, never publish them.
- Judged on: technical execution, innovation, cybersecurity relevance, usability, impact. Judges' decision final.
- Organiser context: Mitigata runs an AI-powered SOC (Gordon AI). Pitch to SOC analysts.
